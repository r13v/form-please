Дизайн API формы

Статус: черновик для обсуждения. Предложенный API ещё не реализован.

Цель — небольшой API для actions отправки, внешних ошибок и согласования строк массива с выбранными ключами. Action связывает кнопку с её проверкой и обработчиком. Внешние ошибки связывают ошибки приложения с полями. Согласование сохраняет состояние строк при изменении выбранных ключей.

Существующий onSubmit верхнего уровня сохраняется как сокращение для action submit. Для остальных новых возможностей обратная совместимость не является ограничением. Изменения механизма выполнения должны соблюдать границы ответственности из ARCHITECTURE.md или явно пересматривать эти границы.

Ограничения дизайна

  • Использовать одну модель отправки для форм с одним или несколькими actions.
  • Сохранить короткий JSX, проверку типов и подсказки редактора.
  • Оставить запросы, преобразование ответов и проверку прав в приложении.
  • Сохранить React Hook Form как владельца редактируемых значений и метаданных полей.
  • Использовать общие типизированные пути входных данных для проверок, внешних ошибок и массивов.
  • Определить публичный контракт до выбора механизма выполнения.

Actions отправки

Предлагаемое использование

const form = kit.useForm(definition, {
  defaultValues,
  actions: {
    approve: {
      implicit: true,
      onSubmit: ({ value }) => approveRequest(value),
    },
    decline: {
      validate: ({ input }) =>
        input.reason.trim()
          ? []
          : [{ path: "reason", message: "Enter a reason." }],
      onSubmit: ({ value }) => declineRequest(value),
    },
  },
})

return (
  <kit.AutoForm form={form}>
    <kit.Submit action={form.actions.decline}>Decline</kit.Submit>
    <kit.Submit action={form.actions.approve}>Approve</kit.Submit>
  </kit.AutoForm>
)

form.actions.decline — объект action, созданный привязкой формы. Это не исходный объект настройки и не строковое имя. Он определяет action и форму, которой оно принадлежит. Объект сохраняет идентичность между рендерами. Следующая отправка использует актуальные настроенные обработчики.

Кнопка получает форму из объекта action. Дополнительный form={form} повторял бы ту же информацию. Если кнопку разместили внутри другой формы, библиотека должна сообщить об ошибке принадлежности до отправки.

Кнопка продолжает использовать слот отправки из kit. Пользовательские слоты получают свойства кнопки, которыми управляет библиотека, и состояние выполнения.

Объекты action и подсказки редактора

<kit.Submit action={form.actions.decline}>Decline</kit.Submit>

Кнопка принимает только объект из form.actions. Строкового варианта нет. form.actions. даёт подсказки свойств, а опечатка в имени — ошибку TypeScript. Дополнительный form={form} не нужен: объект action уже связан с формой.

Один action и сокращение onSubmit

const form = kit.useForm(definition, {
  defaultValues,
  onSubmit: ({ value }) => save(value),
})

<kit.Submit action={form.actions.submit}>Save</kit.Submit>

onSubmit — сокращение для следующей настройки:

const form = kit.useForm(definition, {
  defaultValues,
  actions: {
    submit: {
      implicit: true,
      onSubmit: ({ value }) => save(value),
    },
  },
})

Оба варианта создают одинаковый объект form.actions.submit и используют один механизм отправки. Сокращение сохраняет короткую настройку простой формы и совместимость существующего onSubmit. Для совместимости сохраняется и нативный снимок submitter в данных обработчика. Выбор action от ручного разбора этого снимка не зависит.

Существующая запись <kit.Submit>Save</kit.Submit> тоже сохраняется для сокращения onSubmit: она выбирает form.actions.submit из окружающей формы. Для явно настроенного actions кнопке нужен объект action. Это исключает угадывание action по имени, количеству или порядку кнопок.

onSubmit и actions взаимоисключающие настройки. Библиотека не объединяет их и не задаёт скрытый приоритет. Если нужны несколько actions или дополнительная проверка, приложение использует явный actions.

Редактируемая форма без отправки может не указывать ни onSubmit, ни actions.

Проверка и выполнение

  1. Зафиксировать action, его обработчики и независимый снимок редактируемых входных данных.
  2. Заблокировать повторную отправку формы до начала асинхронной работы.
  3. Проверить общую схему один раз и получить преобразованный результат.
  4. Запустить необязательный validate выбранного action.
  5. Если обе проверки успешны, дождаться выполнения onSubmit этого action.
  6. Снять блокировку после завершения попытки, в том числе при ошибке.

Фиксация и блокировка происходят синхронно в одной точке входа отправки. Другая попытка не может изменить активный action или запустить ещё один обработчик.

validate получает { input, value } одной попытки отправки. Он возвращает список ошибок только для чтения или Promise с таким списком. Пути относятся к входным данным схемы. Проверка не преобразует значения. Обработчик запускается только после успешной проверки общей схемы, поэтому ошибки двух проверок не обязательно появляются одновременно.

Принято: пользователь может увидеть ошибки в два шага. Например, при пустом обязательном name и пустом reason первая отправка показывает только ошибку схемы для name. Ошибку decline.validate для reason показывает следующая отправка. Так validate всегда получает преобразованный value без проверки на отсутствие результата. Отдельная проверка только по input при ошибке схемы — возможный будущий контракт, а не часть первой версии.

onSubmit получает { input, value, form }. Выбранный обработчик уже знает свой action. Ему не нужно разбирать submitter.value.

Ошибки проверки action относятся к выбранной попытке отправки. Они не должны блокировать следующую попытку с другим action до запуска его собственных проверок. При изменении значения поля его ошибки action.validate очищаются. Сама проверка action запускается только при следующей отправке, а проверки schema продолжают следовать настройкам формы. Простое получение фокуса или blur без изменения значения не очищает ошибку.

Отклонённый Promise обработчика не становится автоматически пользовательской ошибкой. Приложение преобразует ожидаемые ошибки через setIssues. Приложение обрабатывает неожиданные ошибки внутри onSubmit. Отдельного onSubmitError или протокола результатов запросов в первой версии нет.

Состояние выполнения

<kit.Submit action={form.actions.decline}>
  {({ isPending }) => (isPending ? "Declining…" : "Decline")}
</kit.Submit>

isPending включает общую проверку, проверку action и его обработчик. Все кнопки отправки отключены, пока выполняется любой action.

Для интерфейса вне кнопки form.submission.action содержит имя активного action или null в состоянии покоя. Потребители этого состояния в React должны обновляться при его изменении. Имена удобны для чтения состояния. Кнопки выбирают action через объект action.

Неявная отправка

В черновике implicit: true указывается внутри самого action. Так выбор action по умолчанию находится рядом с его проверкой и обработчиком, а отдельная строковая ссылка не нужна.

Неявным может быть только один action. Несколько неявных actions — ошибка настройки. При явном actions библиотека не выбирает action автоматически, даже если он один. Сокращение onSubmit явно создаёт неявный action submit.

Enter в обычном однострочном поле запускает неявный action. Без неявного action это взаимодействие не отправляет форму. Enter на кнопке отправки в фокусе запускает action этой кнопки. Многострочные поля, ввод через IME и пользовательские элементы управления сохраняют собственное поведение клавиатуры.

Нативная неявная отправка может активировать первую кнопку отправки. Одной проверки на отсутствие нативного submitter недостаточно для этого контракта. См. правила неявной отправки HTML.

Принято: implicit: true находится внутри action. Отдельного implicitAction на уровне формы нет.

Внешние ошибки

form.setIssues(
  [
    { path: "name", message: "This name is already used." },
    { path: "delegates.2.expiry", message: "Choose a future date." },
    { message: "The source changed. Reload before saving." },
  ],
  { focus: "name" },
)

form.setIssues([])

setIssues заменяет предыдущий набор внешних ошибок. Он не заменяет ошибки схемы или проверки action. Пустой список очищает внешние ошибки. Название яснее передаёт замену набора, чем applyIssues.

Каждая ошибка содержит сообщение и необязательный типизированный путь входных данных схемы. Первая версия использует существующие пути через точку. Пути в виде кортежей не добавляются без потребности конкретной интеграции. TypeScript проверяет пути, заданные в коде. Приложение должно проверять произвольные серверные пути до использования в качестве типизированных путей.

Внешние ошибки появляются сразу. Для этого не нужны состояние touched или предыдущая отправка. Ошибка без пути отображается в слоте ошибок формы.

Изменение значения поля очищает его внешние ошибки. Ошибка без пути сохраняется при редактировании и проверках. Замена набора внешних ошибок или сброс формы очищает предыдущий набор. Повторная проверка сама по себе не очищает внешние ошибки. Следующая отправка позволяет повторить запрос приложения, несмотря на предыдущий отказ сервера.

Фокус на конкретном поле

Принято: focus принимает типизированный путь поля или true:

form.setIssues(issues, { focus: "delegates.2.expiry" })
form.setIssues(issues, { focus: true })
form.setIssues(issues) // Не менять фокус.

Путь выбирает конкретное поле. true выбирает первое доступное поле с ошибкой в порядке регистрации полей React Hook Form, как в разделе Error focus ARCHITECTURE.md. В форме с generated и ручными полями этот порядок может не совпадать с порядком полей в definition. Отдельный обход definition для фокуса не вводится. Строку "first" не используем как специальное значение: в схеме может существовать поле с именем first.

Все ошибки устанавливаются до переноса фокуса в обновлённом интерфейсе. Скрытые и отключённые поля пропускаются. Если явно выбранное поле недоступно, фокус переходит в сводку ошибок, без переключения на случайное другое поле. При focus: true библиотека ищет следующее доступное поле с ошибкой и использует сводку, если таких полей нет. Явный путь может выбрать поле и без ошибки.

Этот контракт фокуса согласован. Фокус пользовательских элементов управления использует существующий контракт ref регистрации поля.

Несколько сообщений для одного поля

Несколько сообщений поддерживаются отдельными issues с одинаковым путём:

form.setIssues([
  { path: "name", message: "Имя уже используется." },
  { path: "name", message: "Выберите другое имя." },
])

Принято: message: string и правило «один issue — одно сообщение». Массив в message не поддерживается. Это сохраняет общий формат со schema и action.validate. Приложение может развернуть массив сообщений сервера при преобразовании ответа:

const messages = ["Имя уже используется.", "Выберите другое имя."]
form.setIssues(messages.map((message) => ({ path: "name", message })))

Ограничение отображения errorDisplay может показывать одно сообщение или все. Оно не удаляет сообщения из состояния ошибок.

Обработка ожидаемых серверных ошибок остаётся в приложении:

const response = await saveRequest(value)
if (!response.ok) {
  form.setIssues(mapSourceErrors(response.errors), { focus: true })
}

Согласование строк массива

Какую проблему решаем

Пользователь выбирает людей, а затем заполняет дополнительные данные для каждого. Когда выбор меняется, нужно сохранить введённые данные оставшихся людей, добавить новых и удалить снятых. При этом ошибки и touched должны остаться у того же человека, даже если его индекс изменился.

Например, у Сэма была ошибка delegates.1.expiry. После удаления Алекса Сэм переходит с индекса 1 на индекс 0. Ошибка должна перейти на delegates.0.expiry, а не остаться на индексе 1 и попасть к новому человеку.

Сопоставление объектов по id сохраняет значения, но само по себе не гарантирует сохранение состояния строки в механизме массивов. Именно эту гарантию должен давать библиотечный reconcile.

Принято: добавить reconcile для явно поддержанных массивов. Приложение решает, когда вызывать операцию. Библиотека отвечает за сохранение данных и состояния строк в рамках её контракта.

Предлагаемое использование

form.array("delegates").reconcile(selectedIds, {
  key: (row) => row.id,
  create: (id) => ({ id, expiry: "" }),
})

array(path) выбирает типизированный путь массива объектов, включая вложенные пути вида teams.${teamIndex}.delegates. Операция читает актуальный массив в момент выполнения. Объект массива не хранит отдельную копию значений формы.

Выбранные ключи определяют состав и порядок строк. key читает ключ строки, который использует приложение. create возвращает полную редактируемую строку для нового ключа. TypeScript проверяет путь, тип строки, тип ключа и создаваемую строку. Ключами могут быть строки или числа.

Где и когда вызывается reconcile

Обычное место вызова — onChange компонента выбора записей. Пользователь выбирает людей в picker, а ниже редактирует срок доступа каждого выбранного человека в строках delegates. Picker передаёт новый список ID. Его обработчик вызывает reconcile один раз для этого нового списка.

В примере DelegatesPicker — компонент приложения, а не новый компонент kit. definition описывает массив delegates и поля его строк.

import { useWatch } from "react-hook-form"

function RequestEditor() {
  const form = kit.useForm(definition, {
    defaultValues,
    onSubmit: ({ value }) => saveRequest(value),
  })
  const rows = useWatch({
    control: form.api.control,
    name: "delegates",
  })

  return (
    <kit.Form form={form}>
      <DelegatesPicker
        selectedIds={rows.map((row) => row.id)}
        onChange={(selectedIds) => {
          form.array("delegates").reconcile(selectedIds, {
            key: (row) => row.id,
            create: (id) => ({ id, expiry: "" }),
          })
        }}
      />
      <kit.Fields />
      <kit.Submit action={form.actions.submit}>Save</kit.Submit>
    </kit.Form>
  )
}

Сценарий вызова:

  1. В форме есть Алекс и Сэм. Пользователь уже ввёл срок для Алекса.
  2. В picker пользователь снимает Сэма и выбирает Марию.
  3. Picker вызывает onChange(["alex", "maria"]).
  4. reconcile сохраняет строку Алекса со сроком, удаляет Сэма и создаёт Марию.
  5. Форма показывает две актуальные строки. Отправка позже сохраняет их обычным action.

Текущий выбор picker выводится из строк формы. Отдельный React state для selectedIds не нужен, поэтому отменённая middleware операция не оставляет picker и строки с разными значениями.

Другой пример — кнопка «Выбрать участников команды»: после получения ID приложение вызывает ту же операцию. Если ID пришли асинхронно, приложение проверяет актуальность ответа перед вызовом.

reconcile не запускается автоматически при отправке или в каждом рендере. Он не нужен при изменении expiry: это обычное редактирование поля. Поиск и фильтрация вариантов picker тоже не вызывают reconcile, пока сам выбор не изменился. При перестановке выбранных ID операция меняет порядок строк.

Зачем нужен create

Выбор содержит только ключи. Из нового ключа библиотека не знает, как получить полную строку формы. create определяет начальные значения её остальных полей.

// До изменения выбора:
[
  { id: "alex", expiry: "2026-12-01" },
  { id: "sam", expiry: "" },
]

// Пользователь оставил Алекса и выбрал Марию:
form.array("delegates").reconcile(["alex", "maria"], {
  key: (row) => row.id,
  create: (id) => ({ id, expiry: "" }),
})

// Результат:
[
  { id: "alex", expiry: "2026-12-01" },
  { id: "maria", expiry: "" },
]

Алекс уже есть: его строка сохраняется, create("alex") не вызывается. Сэм снят с выбора: его строка удаляется. Марии ещё нет: create("maria") создаёт её строку с пустым expiry.

Если строка содержит другие поля, приложение определяет их начальные значения:

form.array("delegates").reconcile(selectedIds, {
  key: (row) => row.id,
  create: (id) => ({ id, expiry: "", access: "read", notify: false }),
})

Если поменялся только порядок, например ['sam', 'alex'], create вообще не вызывается. Он нужен для новых строк, а не для обновления существующих.

Наблюдаемый контракт

  • Сохранённые строки сохраняют редактируемые данные и идентичность строки в механизме выполнения.
  • Состояние touched и ошибки строки следуют за сохранённой строкой к новому индексу.
  • Удалённые строки теряют значения и относящиеся к ним метаданные.
  • Для каждого нового ключа create вызывается один раз и создаёт новую строку.
  • Порядок результата совпадает с порядком переданных ключей.
  • Состояние dirty пересчитывается относительно default values, а не копируется.
  • Согласование не гарантирует ссылочное равенство объектов.

Повторяющиеся выбранные ключи или повторяющиеся ключи текущих строк — ошибки. Созданная строка должна содержать запрошенный ключ. Эти проверки завершаются до изменения массива. Если создание строки завершается ошибкой, массив остаётся прежним. Неизменившийся выбор не создаёт строки и не публикует изменение значений.

Ошибки сохранённых строк включают ошибки схемы, проверки action и внешние ошибки. Согласование не очищает их так, будто перемещение индекса было редактированием поля. Ошибка самого массива остаётся связанной с массивом. Следующая проверка может её заменить.

Согласование — одна управляемая операция изменения значений. Она следует политике обновлений формы, может быть отменена и занимает один шаг истории, если история включена. Операция должна сохранять состояние через механизм массивов, а не только присваивать новый массив значений. Поведение выбора записей остаётся в приложении или наборе элементов управления.

Согласованные решения

  • Кнопки выбирают action через объект из form.actions, без строкового варианта.
  • implicit: true находится внутри action.
  • onSubmit сохраняется как сокращение для неявного action submit.
  • В тексте используется термин action.
  • focus принимает типизированный путь поля или true. Без focus положение фокуса не меняется.
  • При изменении значения поля его ошибки action.validate очищаются. Сама проверка запускается только при следующей отправке.
  • message остаётся строкой. Несколько сообщений передаются отдельными issues с одним path.
  • Неожиданные ошибки обрабатывает приложение внутри onSubmit.
  • action.validate запускается только после успешной проверки схемы. Ошибки двух проверок могут появляться в два шага.
  • focus: true выбирает поле в порядке регистрации React Hook Form.
  • При редактировании очищаются ошибки action и внешние ошибки на изменённом пути и его родительских или дочерних путях, без dependsOn.
  • Актуальность серверного ответа перед setIssues проверяет приложение.
  • Фокус пользовательских controls использует существующий ref-контракт.
  • Добавляем reconcile для явно поддержанных массивов. Точные границы поддержки уточняются отдельно.

Ошибки action после редактирования

Пользователь нажал Decline с пустым reason и получил сообщение «Введите причину». Затем он изменил reason. Ошибка этого поля исчезает сразу. decline.validate повторно запускается только при следующей отправке. Если введённая причина всё ещё не подходит, следующая отправка снова покажет ошибку. Исчезновение сообщения не означает, что проверка уже прошла.

Это согласованный вариант. Он не запускает потенциально асинхронную проверку при каждом вводе. Для связанных полей принято очищать ошибки по изменённому пути и его родительским или дочерним путям. Ошибка соседнего поля сама по себе не исчезает.

Принятые варианты и обоснования

Ниже сохранено сравнение вариантов для принятых решений. Открытыми остаются точные границы поддержки reconcile, перечисленные в конце.

Формат нескольких сообщений

Несколько ошибок могут относиться к одному пути. Принят один формат для schema, action.validate и setIssues.

Вариант Плюсы Минусы
message: string, отдельный issue на каждое сообщение Один формат ошибки. Сообщения отдельно отображаются и фильтруются. В ответе сервера массив сообщений нужно развернуть в несколько issues.
message: string | readonly string[] Можно передать массив сервера без разворачивания. Каждый потребитель обрабатывает два типа. Всё равно нужна нормализация для слотов.
Только messages: readonly string[] Один тип. Сообщения одного поля сгруппированы. Даже одно сообщение требует массива. Формат отличается от существующего issue schema.

Принято: оставить message: string. Несколько issues с одним path уже выражают нужную информацию. Пример преобразования массива сервера приведён в разделе внешних ошибок.

Неожиданная ошибка обработчика

Серверный отказ, который приложение ожидает, преобразуется в issues. Исключение из-за сбоя сети или ошибки кода требует отдельной обработки. Библиотека не может выбрать подходящее пользовательское сообщение.

Вариант Плюсы Минусы
Приложение обрабатывает исключения внутри onSubmit Новый API не нужен. Приложение различает ожидаемый отказ, сеть и ошибку кода. В нескольких actions обработка может повторяться.
Общий onSubmitError(error, details) в настройках формы Один обработчик для всех actions. Можно централизованно вызвать уведомление и журналирование. Новый callback и правила его собственной ошибки. Нужно определить состав details.
Обработчик возвращает результат вида success или failure Ожидаемые исходы выражены типами. Новый протокол запросов. Брошенные исключения всё равно требуют обработки.

Принято: в первой версии оставить обработку в приложении, внутри onSubmit. Приложение может использовать существующий общий обработчик ошибок во всех actions. Общий onSubmitError оправдан, если такая обработка повторяется и не укладывается в короткий код приложения.

При любом варианте библиотека снимает блокировку в случае исключения. Она не преобразует неизвестное исключение в issue и не считает его успехом. Само исключение не следует молча поглощать. Необработанное исключение не имеет гарантированного пользовательского отображения; приложение отвечает за него.

Очистка ошибок связанных полей

Пример: правило проверяет start и end, но issue находится на end. Пользователь исправил start. По одному пути end библиотека не знает, что изменение start могло исправить ошибку.

Вариант Плюсы Минусы
Очищать только ошибки изменённого пути и связанных родительских или дочерних путей Простое правило. Посторонние ошибки остаются. Ошибка на соседнем поле может остаться до отправки.
Очищать все ошибки action и все внешние ошибки полей при любом изменении Не нужны зависимости. Не остаются ошибки соседнего поля от старых значений. Исправление одного поля скрывает ошибки других полей.
Добавить к issue список зависимостей, например dependsOn Точная очистка ошибок связанных полей. Новый публичный контракт зависимостей. Серверный адаптер должен знать эти зависимости.

Принято: выбрать первый вариант без dependsOn. Изменение address.city очищает issues на address.city и address. Замена всего address очищает issues его дочерних полей. Ошибка address.zip не исчезает от изменения address.city. Сравнение путей идёт по сегментам, а не по строковому префиксу.

Общие issues без пути сохраняются. Ошибки schema остаются под управлением её обычной проверки. Для внешних ошибок приложение может явно заменить набор через setIssues. Ошибки action на соседних полях заменяются следующей проверкой этого action. Если этого недостаточно в реальных формах, вернёмся к зависимостям.

Ответ сервера после изменения значений

Пример: отправлено имя alex. Пока запрос выполнялся, пользователь изменил его на maria. Сервер сообщил, что alex уже используется. Применить эту ошибку к текущему maria было бы неверно.

Вариант Плюсы Минусы
Приложение проверяет актуальность ответа перед setIssues Метод остаётся небольшой операцией установки ошибок. Приложение знает смысл запроса и ключи записей. Сравнение со снимком или номером запроса нужно написать в приложении.
setIssues получает снимок или токен отправки Библиотека может отбрасывать устаревшие ошибки. Нужно определить, как сравнивать поля, массивы, файлы и изменения, которые пользователь отменил.
Запретить редактирование на время отправки Значения не меняются от пользовательского ввода во время запроса. Интерфейс блокирует исправления. Программные изменения и reset всё равно возможны.

Принято: оставить проверку актуальности приложению. setIssues применяет переданный набор к текущей форме и не угадывает, к какому запросу он относится. Обработчик получает снимок input для сравнения. Приложение может отбросить устаревший ответ целиком или только ошибки изменённых полей.

Для массива одного сравнения значения по индексу недостаточно: строка могла переместиться или быть удалена. Приложение сопоставляет ответ с ключом записи и находит её актуальный путь. Ошибки конфликта версии тоже требуют решения приложения: устаревшее значение поля не всегда делает конфликт неактуальным.

Фокус пользовательских элементов управления

Нативное поле обычно имеет фокусируемый input. Пользовательский control может содержать несколько элементов или скрывать настоящий input за видимой кнопкой. Нужно определить, какой элемент библиотека умеет фокусировать.

Вариант Плюсы Минусы
Использовать существующий контракт ref регистрации поля Новый API не нужен. Generated controls и корректно подключённые ручные поля используют один принцип. Для составного control приложение должно передать ref на правильный элемент.
Искать элемент в DOM по name или другим атрибутам Может работать без подключения ref. Неоднозначность составных controls. DOM не сообщает надёжно, какой элемент должен получать фокус.
Добавить отдельную регистрацию focus(path, callback) Поддерживает необычные controls и пользовательскую логику открытия. Вторая система регистрации. Нужно определить размонтирование и доступность control.

Принято: использовать существующий ref-контракт. Гарантировать фокус для смонтированного доступного элемента, корректно подключённого к регистрации поля. Для составного control приложение выбирает элемент, который принимает фокус. Без подходящего ref используется сводка ошибок.

Библиотека не открывает скрытые секции и не меняет состояние приложения ради фокуса. Новую регистрацию имеет смысл добавить только после примера control, который невозможно подключить через существующий контракт.

Reconcile для массивов

Польза reconcile возникает, когда нужно сохранять row identity, touched и ошибки при изменении состава и порядка строк. Одного короткого сопоставления значений для обоснования публичного метода недостаточно.

Вариант Плюсы Минусы
Оставить сопоставление в приложении Новый API и обязательства библиотеки не нужны. При проблеме с metadata приложение вынуждено координировать операции массива.
Добавить reconcile для явно поддержанных массивов Решает задачу сохранения состояния. Ограничения можно проверить и описать. Потребуются гарантии для ошибок, вложенных строк, middleware и history.
Поддержать произвольное глубокое согласование сразу Один метод для сложных деревьев массивов. Большой контракт. Трудно сохранить identity при одновременном изменении нескольких уровней.

Принято: добавить reconcile для явно поддержанных массивов. Операция сохраняет данные, row identity, touched и ошибки сохранённых строк. Неподдержанный случай должен давать ошибку до изменения значений, а не незаметно терять metadata. Произвольное глубокое согласование всего дерева массивов не входит в выбранный вариант.

Открытые границы reconcile

Решение добавить метод принято. Следующие вопросы определяют его точную область поддержки и не отменяют это решение.

Вложенные массивы

Предложение: одна операция согласовывает один выбранный массив. При перемещении сохранённой родительской строки состояние её вложенных строк следует за ней. Это не означает отдельного согласования состава всех вложенных массивов. Нужно определить, для каких вложенных структур библиотека гарантирует это поведение и как сообщает о неподдержанной структуре до изменения значений.

Изменения через middleware

Предложение: разрешать отмену операции и изменение обычных значений, но запрещать изменение состава, порядка и ключей выбранного массива за пределами предложения reconcile. Более широкий контракт потребует повторного согласования по итоговому предложению. Это ограничение ещё не согласовано.

Это решения о публичном API. Черновик не задаёт реализацию механизма выполнения и не является разрешением менять код библиотеки.
