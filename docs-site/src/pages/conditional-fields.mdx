# Conditional fields

Use a synchronous resolver when a UI property depends on form values or runtime
context. A resolver returns the property value for the current form state.

## Show or hide a field

Set `visible` to a resolver that returns a boolean:

```tsx
// [!include ~/snippets/lab-profile-form.tsx:conditional-field]
```

When `accountType` changes, Form, Please resolves the UI tree again. The
`companyName` field appears only for a company account.

`visible` has these effects:

- A hidden node does not render.
- A hidden section or array does not render its descendants.
- A hidden field keeps its value, and the schema still validates it.

See [Hidden fields keep their
values](/how-it-works#hidden-fields-keep-their-values).

## Derive field properties

Field properties can use the same form values:

```tsx
// [!include ~/snippets/conditional-fields-guide.tsx:derived-field]
```

On an ordinary definition node, the first resolver argument is the complete,
deeply readonly schema input. A resolver authored inside a reusable fragment
receives that fragment's local input instead.
It is not only the value at the field path.

These field properties accept a static value or a synchronous resolver:

| Property | Result | Default |
| --- | --- | --- |
| `visible` | Shows or hides the field. | `true` |
| `disabled`, `readOnly` | Changes the control interaction state. | `false` |
| `required` | Passes required UI state to the control. | `false` |
| `label`, `description` | Changes displayed content. | No content |
| `props`, `slotOptions` | Changes control props or slot configuration. | Control-dependent |

Layout properties such as `className` and `span` also accept resolvers. See
[Definitions](/definitions#resolver-values) for the complete property reference.

Ordinary resolvers must return immediately. A resolver that returns a promise
causes a runtime error. Keep resolvers small and free of side effects. Do not
fetch data or update form state in an ordinary resolver.

A selectable field's `options` property has a separate function contract. It
may return a promise and tracks the `values` and `context` properties it reads.
See [Async options](/definitions#async-options).

## Apply one condition to a group

applies to all descendants:

```tsx
// [!include ~/snippets/conditional-fields-guide.tsx:conditional-section]
```

A descendant cannot override inherited state:

- A hidden parent hides all descendants.
- A disabled parent disables all descendants.
- A read-only parent makes all descendants read-only.

`required` is a field property. It is not inherited from a section or array.

## Use resolvers inside arrays carefully

An array-child resolver receives the complete root input. It does not receive
the current row or its index. Therefore, the same resolver result applies to
each generated row for a given form state.

Use an array-node resolver for conditions that depend on the complete array:

```tsx

```

Keep row and cross-row validation in the Standard Schema. Use custom array UI
when the UI condition must depend on the current row index. See [Arrays](/arrays)
for custom operations and array slots.

## Split a form into variants

Some forms have variants with different fields. A personal account needs a
first name and a last name. A company account needs a company name and a VAT ID.
One flat schema with optional fields mixes the two variants. Each field then
needs its own `visible` and `required` resolvers, and all variant fields are
optional in the output type.

Write one object schema for each variant. Join the variants with
`z.discriminatedUnion`:

```tsx
// [!include ~/snippets/account-variants.tsx:schema]
```

- `accountBase` contains the fields that all variants share.
- Each variant extends `accountBase` with its own fields.
- The discriminator `accountType` has a different literal value in each variant.
- `.prefault("")` validates a missing value as an empty string. The fields of
  the other variant are not in `defaultValues`, so they are `undefined` after a
  switch. Without `.prefault("")`, the schema shows `Invalid input: expected
  string, received undefined` instead of your messages. Do not use
  `.default("")`, because it skips the `.min(1)` rule.
- `defaultValues` need only the shared fields and the discriminator, such as
  `{ accountType: "personal", email: "" }`.

Put the fields of each variant in one section. Show the section only when the
discriminator selects its variant:

```tsx
// [!include ~/snippets/account-variants.tsx:definition]
```

Select **Company** and submit the empty form. The form shows issues only for the
company fields and the email. Complete the fields and submit again. The output
contains only the company variant.

The definition has these parts:

- The `accountType` field selects the variant. The `radio` control writes one
  of the literal values.
- Each section has one `visible` resolver. The variant fields do not need
  resolvers, so they use a static `required: true`.

Hidden fields keep their values. See [Hidden fields keep their
values](/how-it-works#hidden-fields-keep-their-values). The schema validates
only the selected variant. `z.object` removes unknown keys by default, so the
output does not contain the fields of the other variant. Do not use
`z.looseObject` for a variant, because it keeps those keys.

`onSubmit` receives a union value. Compare `value.accountType` to narrow it to
one variant. Resolvers receive the same union input, and the same comparison
narrows it.

| Concern | One object with optional fields | Discriminated union |
| --- | --- | --- |
| Schema | Optional fields and a `superRefine` rule for each condition. | One object schema for each variant. |
| Definition | `visible` and `required` resolvers on each variant field. | One `visible` resolver on each variant section. |
| Output type | All variant fields are optional. | A union that `accountType` narrows. |
| Values of the other variant | A transform must remove them. | The selected variant schema removes them. |

The union can also be at a nested path. Then field paths include the parent
key, such as `account.companyName`. A reusable fragment cannot be placed at a
union scope, because the scope does not satisfy the input of one variant. Put
the variant fields directly in the section.

## Keep conditional validation in the schema

`visible` and `required` do not change schema rules. See [`required` is
UI-only](/how-it-works#required-is-ui-only).

Express the same condition in the Standard Schema:

```tsx
// [!include ~/snippets/conditional-fields-guide.tsx:conditional-schema]
```

This schema requires `companyName` only for a company account. Its transform
also removes a stale `companyName` from personal-account output. When each
account type has its own set of fields, use a discriminated union instead. See
[Split a form into variants](#split-a-form-into-variants).

Use a schema transform when cleanup is part of the submission contract. Use
value middleware when the source and cleared value must commit atomically. Use
`form.update` for the same managed boundary in an application action. See
[Value middleware](/middleware).
