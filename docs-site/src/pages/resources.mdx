# Resource state

Show the state of a request in the form. While countries load, the country
field can show a loading message and stay disabled. When the request fails, the
field can show the error.

## Show a request in a field

Put the request state in the form context as a `ResourceState`. Then read it in
the field properties.

```tsx

```

Select a request state. The options, description, and disabled state change
together.

`matchResource` requires one callback for each state. TypeScript reports an
error when a state has no callback.

## Connect a request library

Your request library keeps ownership of requests, retries, cancellation, and
caching. Convert its result to a `ResourceState` and pass it as context:

```tsx
// [!include ~/snippets/resources-guide.tsx:query-context]
```

When the query changes, the component supplies a new context. The field
properties then resolve again with the current state.

This approach has these advantages:

- The form definition does not load data. You can test it with a fixed context.
- The request library stays the only owner of requests and cache.
- One request state controls several field properties.

:::tip
For a plain option list without loading or error UI, an async field
`options` function is sufficient. See
[Async options](/definitions#async-options).
:::

### Keep data after a failed background refresh

The `toResource` function above maps a failed background refresh to `error`.
The field then loses the loaded options. This adapter keeps the loaded data and
reports the refresh state separately:

```ts twoslash
// [!include ~/snippets/query-to-resource.ts]
```

Use `queryToResource` in place of `toResource`. The adapter maps query states
as follows:

| Query result | Resource result |
| --- | --- |
| Initial load | `pending` |
| Loaded data | `success` |
| Failed background refetch with old data | `success` with `refresh.error` |
| Failed request without data | `error` |

The background refetch error stays in the success branch because usable data
still exists. The UI can keep the options and report the refresh error. The
top-level error branch does not contain previous data.

`QueryResourceState` adds `fetchStatus` and `refresh` properties to the basic
three-state shape. `matchResource` and `fromResource` keep these extra
properties when they narrow a branch.

See [Creative studio policies](/examples/studio-policies) for a live form with
saved options and background refresh state.

### Share one selector across properties

`fromResource(select, cases)` creates a UI resolver. It calls `select` with the
form values and resolver details, then runs the callback for the current state.
Use it when several properties read the same resource:

```tsx
// [!include ~/snippets/resources-guide.tsx:shared-selector]
```

Each `fromResource` callback receives these arguments in this order:

1. The narrowed resource state.
2. The complete readonly form input.
3. Resolver details, which contain the readonly form context.

## Reference

### `ResourceState`

`ResourceState<Value, Error>` is a readonly tagged union with three states:

```ts
type ResourceState<Value, Error = unknown> =
	| { readonly status: "pending" }
	| { readonly status: "success"; readonly value: Value }
	| { readonly status: "error"; readonly error: Error }
```

The `status` property selects the branch. A successful state must contain
`value`. An error state must contain `error`. Set the `Error` type when a
callback reads a known error property. The default error type is `unknown`.

### Helpers

| Required result | Helper |
| --- | --- |
| Derive a value from a resource now | `matchResource` |
| Create a synchronous UI resolver from a selector | `fromResource` |
| Load or refresh remote data | Application code or a request library |
| Load one selectable list without request UI | Async field `options` |

Each callback receives the narrowed state:

| Callback | Available state data |
| --- | --- |
| `pending` | `status` |
| `success` | `status`, `value` |
| `error` | `status`, `error` |

The result type is the union of the three callback results. Keep the results
compatible when a caller requires one specific type.

UI resolvers are synchronous. The selector and all callbacks must return
synchronously. Load data before or beside the form. Do not pass an `async`
function to `fromResource`. Field `options` has its own async contract.

### Invalid states and callback errors

TypeScript prevents unsupported status values in typed application code. At
runtime, both helpers throw a `TypeError` for an unsupported status. They do not
catch errors that a selector or callback throws.

Keep resource objects inside the supported union. Handle request failures when
you create the resource. Handle UI conversion failures where you call the
helper.
